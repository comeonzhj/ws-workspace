从 Markdown 到 HTML 工作台
Agent × 人类的协作新范式

Agent 不再把 Markdown 塞进聊天窗口，而是维护一个可交互的 HTML 页面。 人类直接在页面上操作，Agent 读取状态继续推进。 信息不再"读后即焚"，而是在网页上持续生长。

↓ 看看它是怎么工作的
范式转换
从"读 Markdown"到"操作工作台"
Thariq 在《The Unreasonable Effectiveness of HTML》中指出 HTML 比 Markdown 更适合作为 Agent 输出。 我们在此基础上更进一步：让 HTML 成为双向协作的介质。
Before · Markdown

线性对话，读后即焚

Agent 输出一大段 Markdown → 人类读完 → 用自然语言回复 → Agent 再输出。 上下文存在于对话流中，滚动即消失。信息密度低，无法交互。

Agent: 这是 Q2 的功能优先级... 1. 功能 A (P0) 2. 功能 B (P1) 3. 功能 C (P2) 你觉得怎么样？ Human: 功能 B 应该提到 P0， 功能 A 降到 P1 Agent: 好的，更新一下... 1. 功能 B (P0) 2. 功能 A (P1) ...
→
After · HTML 工作台

持续生长，双向交互

Agent 通过指令往页面注入组件 → 人类直接拖拽、选择、填写 → Agent 读取结构化状态继续推进。 页面是持久的画布，信息在上面积累而非流走。

Agent CLI: ws add kanban \ --columns "想法,评估中,已确认,开发中" Agent CLI: ws add decision-card \ --question "先做哪个？" \ --options "功能A|功能B|功能C" [用户在页面上拖拽卡片，点选方案] Agent API: GET /api/state → { "selected": "功能B", "kanban": { "已确认": ["功能B"] } } Agent: 收到，我按功能B优先来推进...

组件体系
Agent 用指令，不用写代码
每个 ws add 命令生成一个自包含的 Web Component。Agent 不碰 HTML/CSS/JS，只描述意图。
📋

Kanban 看板

可拖拽的多列看板。用于优先级排序、状态跟踪、任务分拣。

ws add kanban --columns "待办,进行中,完成"
🤔

Decision Card 决策卡

单选题 + 备注。用于方案选择、A/B 决策、方向确认。

ws add decision-card --question "选哪个？" --options "A|B|C"
✅

Todo List 待办

可勾选的任务列表。用于 checklist、行动项、验收标准。

ws add todo-list --title "上线前检查" --items "测试,文档,部署"
📝

Form 表单

结构化输入：文本、下拉、多行。用于收集参数、配置、反馈。

ws add form --fields '[{"name":"title","type":"text"}]'
📊

Table 表格

数据表格展示。用于对比矩阵、规格参数、人员分配。

ws add table --headers "功能,优先级,负责人"
✏️

Rich Editor 编辑器

富文本编辑区。用于自由书写、头脑风暴、方案描述。

ws add rich-editor --placeholder "写下你的想法..."
📌

Heading 标题

标题 + 副标题。用于分区、章节标注、上下文说明。

ws add heading --text "第二轮：技术方案" --level 1
🧩

更多组件…

投票器、时间线、思维导图、图片标注。组件体系可扩展。

ws add vote --question "给方案打分" --scale 5

技术架构
三层设计
CLI 做主干（Agent 的手），MCP 做实时通道（Agent 的耳），Skill 做使用指南（Agent 的脑）。

CLI 层 — Agent 的手

  • Agent 的主要接口，跟调 shell 命令一样
  • ws init · ws add · ws state · ws update
  • 每个操作都是声明式的，不碰前端代码
  • 返回 JSON，Agent 可直接解析
$ ws add kanban --columns "想法,评估中,已确认" $ ws state get --component kanban-1 → { "想法": ["功能A","功能B"], "评估中": [] }

MCP 层 — Agent 的耳

  • WebSocket 双向通道，实时监听用户操作
  • wait_for_user — Agent 可暂停等待交互
  • 用户拖拽/选择/填写 → 结构化事件推送
  • 适合需要"等人类做决定"的场景
mcp.workspace.wait_for_user({ component: "decision-card-1", timeout: 300 }) → { selected: "方案B", comment: "更完整" }

服务器 — 状态中枢

  • Express + WebSocket，同时做静态服务和 API
  • 维护全局状态 JSON（组件列表 + 事件日志）
  • REST API 供 CLI/MCP 调用
  • WebSocket 推送给浏览器实时刷新

前端 — 可交互页面

  • 单 HTML 文件 + 内联 Web Components
  • 暖色调浅色主题，卡片式布局
  • 用户操作自动同步到服务器
  • 未来可导出为独立 HTML 离线使用

部署模式

  • 本地模式（默认）：ws init 在本机起服务，localhost 访问。适合个人开发、单人协作。
  • 云端模式（可选）：服务部署在云服务器，公网 IP + 端口访问。适合远程协作、团队共享、演示。
  • 离线模式（规划中）：导出为单个 HTML 文件，所有状态内嵌，无需服务器。适合邮件分享、归档。
